**Модуль 3. Проектирование вычислительной архитектуры ИИ-систем**

**ОПОРНЫЙ КОНСПЕКТ ЛЕКЦИЙ**

**Лекция 3.1. Методология выбора аппаратно-программной платформы (HW/SW Co-Design)**

**1. Цель лекции**
Научить студентов переводить бизнес-задачу в инженерные требования к аппаратному обеспечению, используя компромиссный анализ и формализованные методы принятия решений.

**2. Формируемые компетенции**

* HPC-1 (индикатор HPC-1.1) — обеспечивает выбор наилучшей вычислительной архитектуры под задачу ИИ.

**3. Основные вопросы**

3.1. Треугольник ограничений ИИ-систем

* В основе кодизайна лежит триада противоречий: Accuracy (точность), Latency/Throughput (скорость), Power & Cost (энергия/бюджет).

* Latency ограничена пропускной способностью памяти при batch=1; Throughput ограничена пиковой вычислительной мощностью Tensor Cores.

* TCO (Total Cost of Ownership) включает цену железа, охлаждение, электроэнергию, амортизацию.

* Три ключевых компромисса: Accuracy↔Performance, Performance↔Efficiency, Accuracy↔Efficiency.

* Метод «Жёстких границ» (Hard Constraints): пример для турникета метро — Latency < 150 мс, Power < 10 Вт, Accuracy > 95%.

3.2. Уровни абстракции кодизайна

* Algorithmic level — выбор архитектуры DNN (CNN, Transformer, MLP).

* System level — пропускная способность памяти (HBM/DDR) vs вычислительная мощность (FLOPS), Memory Wall.

* Circuit level — форматы данных (FP32, FP16, INT8), специализированные блоки (Tensor Cores).

* Пример сквозного кодизайна для Edge-сервера OCR: переход решения между тремя уровнями.

3.3. Матрица принятия решений (Weighted Decision Matrix)

* WDM формализует выбор платформы через таблицу «альтернативы × критерии» с весами и оценками.

* Формирование критериев по методологии P-C-S-E: Performance, Cost, Software & Ecosystem, Environment & Scalability.

* Hard Constraints получают вес 0.9–1.0; остальные критерии распределяются методом AHP или через денежный эквивалент.

3.4. Обзор аппаратных платформ

* GPU (NVIDIA) — массовый параллелизм, экосистема CUDA, универсальность.

* TPU/NPU (Google, Amazon, Huawei) — систолический массив, высокая энергоэффективность.

* FPGA (Xilinx, Intel) — программируемая логика, детерминированная низкая задержка.

* Edge ASIC (Apple Neural Engine, Movidius, Edge TPU, Hexagon) — фиксированная архитектура, сверхнизкое энергопотребление.

**4. Ключевые определения (инженерный словарь)**

* TCO — совокупная стоимость владения платформой на всём жизненном цикле.

* WDM (Weighted Decision Matrix) — таблица взвешенного сравнения альтернатив по критериям.

* Hard Constraint — жёсткое ограничение, невыполнение которого делает альтернативу неприемлемой.

* Memory Wall — разрыв темпов роста пропускной способности памяти и вычислительной мощности.

* Co-Design — совместная оптимизация алгоритма и архитектуры платформы.

**5. Таблицы сравнения**

| Уровень абстракции | Что определяется | Пример решения |
| :---- | :---- | :---- |
| Algorithmic | Архитектура модели (CNN/Transformer) | Замена LSTM на Attention с малой размерностью |
| System | Пропускная способность памяти vs FLOPS | Переход в compute-bound через рост AI |
| Circuit | Разрядность данных (FP32/FP16/INT8) | Квантизация весов под NPU без поддержки FP32 |

**6. Итоги (инженерные выводы)**

1. Выбор платформы — это компромисс между точностью, скоростью и стоимостью, формализуемый через WDM.

2. Кодизайн охватывает три уровня абстракции: алгоритм, систему и схему — решение на одном уровне влияет на остальные.

3. Жёсткие ограничения (Hard Constraints) должны быть выявлены на самом раннем этапе и отбрасывать неподходящие альтернативы сразу.

4. Универсальных платформ не существует: GPU — гибкость, TPU/NPU — энергоэффективность, FPGA — детерминированная задержка, Edge ASIC — минимальное энергопотребление.

**Лекция 3.2. Расчёт ресурсов (Compute Estimation & Profiling)**

**1. Цель лекции**
Сформировать умение численно оценивать требования к памяти, вычислительной производительности и времени выполнения для обучения и инференса моделей ИИ.

**2. Формируемые компетенции**

* HPC-1 (индикатор HPC-1.2) — разрабатывает эффективные вычислительные реализации параллельных алгоритмов ИИ.

**3. Основные вопросы**

3.1. Оценка объёма памяти для обучения

* Формула: Total VRAM = Weights + Gradients + Optimizer States + Activations + Overheads.

* Model Weights: FP32 = 4 байта/параметр, FP16/BF16 = 2 байта, INT8 = 1 байт.

* Optimizer States — самый прожорливый компонент: Adam/AdamW требует 8 байт на параметр (FP32) для хранения Momentum и Variance.

* Пример Llama-2 7B (FP16+Adam): веса 14 ГБ + градиенты 14 ГБ + Adam 56 ГБ = 84 ГБ без активаций — не влезает в A100 80 ГБ.

3.2. Оценка FLOPS для инференса

* Fully-Connected: FLOPs = 2 × in_features × out_features (умножить на batch).

* Conv2D: FLOPs = 2 × kh × kw × in_ch × out_ch × H_out × W_out.

* Attention: FLOPs = 8 × seq_len × d_model² + 4 × d_model × seq_len².

* Пример Llama-2 7B: ~28.6 TFLOP на один токен (32 слоя).

3.3. Arithmetic Intensity (AI) и Roofline Model

* AI = FLOPs / Bytes. Низкая AI (< 1) → memory-bound; высокая AI (> 100) → compute-bound.

* Ridge Point: AI_ridge = Peak FLOP/s / Peak Bandwidth. Для A100: 312/2000 = 156 FLOP/byte.

* Увеличение batch size, квантизация и fusion операций повышают AI, переводя оператор в compute-bound режим.

3.4. Инструменты профайлинга

* NVIDIA Nsight Systems — системный уровень: timeline CPU/GPU, поиск простоев и неэффективных пересылок.

* NVIDIA Nsight Compute — детальный анализ ядра: Occupancy, причины остановок (Warp Stall).

* PyTorch Profiler (torch.profiler) — измерение времени и памяти операторов на уровне фреймворка.

**4. Ключевые определения (инженерный словарь)**

* Arithmetic Intensity (AI) — отношение FLOPs к объёму переданных данных (байт).

* Ridge Point — точка перехода между memory-bound и compute-bound режимами на Roofline-диаграмме.

* Occupancy — доля активных варпов на потоковом мультипроцессоре GPU.

* Gradient Checkpointing — рекомпьютация активаций для экономии памяти за счёт времени.

* ZeRO — метод шардирования состояний оптимизатора, градиентов и весов между GPU.

**5. Таблицы сравнения**

| Компонент памяти | Формула | Пример (Llama-2 7B, FP16+Adam) |
| :---- | :---- | :---- |
| Веса | Params × Precision | 14 ГБ |
| Градиенты | = размеру весов | 14 ГБ |
| Optimizer States (Adam) | Params × 8 байт | 56 ГБ |
| Итого (без активаций) | Сумма компонентов | 84 ГБ |

**6. Итоги (инженерные выводы)**

1. Оценка ресурсов должна выполняться «на бумаге» до запуска кода — это позволяет заранее выявить нехватку памяти.

2. Optimizer States в Adam — крупнейший потребитель памяти при обучении, что часто становится причиной OOM.

3. Roofline Model даёт быстрый ответ на вопрос, какой ресурс (FLOPS или память) ограничивает конкретный оператор.

4. Профайлинг — обязательный этап, переходящий от общего анализа (Nsight Systems) к детальному разбору проблемного ядра (Nsight Compute).

**Лекция 3.3. Распределённое обучение (Distributed Training)**

**1. Цель лекции**
Дать системное понимание организации обучения больших моделей на сотнях и тысячах ускорителей с использованием стратегий параллелизма и шардирования состояний.

**2. Формируемые компетенции**

* HPC-1 (индикатор HPC-1.2) — разрабатывает эффективные вычислительные реализации параллельных алгоритмов ИИ на современных архитектурах.

**3. Основные вопросы**

3.1. Стратегии параллелизма (3D-параллелизм)

* Data Parallelism (DP) — каждая GPU хранит полную модель и обрабатывает разные данные; синхронизация градиентов через All-Reduce.

* Pipeline Parallelism (PP) — разбиение слоёв модели на стадии; коммуникация ограничена передачей активаций между стадиями.

* Tensor Parallelism (TP) — разрезание весов внутри слоя; требует сверхбыстрого соединения (NVLink), не масштабируется за пределы узла.

* Гибридная схема (Megatron-Turing): TP внутри узла, PP между узлами, DP между группами узлов.

3.2. Коммуникационные библиотеки

* NCCL — стандарт де-факто для GPU-коммуникаций.

* Коллективные операции: All-Reduce (синхронизация градиентов в DP), All-Gather (сборка тензоров при TP), Reduce-Scatter, Broadcast, Send/Recv (передача активаций в PP).

3.3. Законы масштабирования

* Закон Амдала: S(P) = 1 / (s + (1-s)/P), где s — доля последовательного кода.

* Strong Scaling — фиксированная задача при росте числа GPU; Weak Scaling — задача растёт пропорционально числу GPU.

3.4. Оптимизаторы для больших батчей и шардирование состояний

* LARS и LAMB — адаптивные оптимизаторы, позволяющие обучение со сверхбольшими батчами (до 32–65 тыс.).

* ZeRO-1/2/3 — шардирование состояний оптимизатора, градиентов и весов соответственно.

* FSDP — реализация ZeRO-3 в PyTorch, позволяющая обучать модели, в десятки раз превышающие память одной GPU.

**4. Ключевые определения (инженерный словарь)**

* All-Reduce — коллективная операция суммирования/усреднения тензоров со всех устройств с последующей рассылкой результата.

* Pipeline Bubble — простой устройства при пайплайн-параллелизме из-за ожидания зависимых стадий.

* ZeRO (Zero Redundancy Optimizer) — метод устранения избыточного хранения состояний модели между GPU.

* FSDP (Fully Sharded Data Parallel) — реализация ZeRO-3 в PyTorch.

* Strong/Weak Scaling — два режима оценки масштабируемости распределённых вычислений.

**5. Таблицы сравнения**

| Стратегия | Назначение | Ограничение | Применение |
| :---- | :---- | :---- | :---- |
| DP | Масштабирование по данным | Модель влезает в GPU | Модели < 1B |
| PP | Разрезание по слоям | Пузыри, балансировка | Модели > 10B на многих узлах |
| TP | Разрезание внутри слоя | Огромная коммуникация | Только внутри узла с NVLink |
| FSDP (ZeRO) | Шардирование состояний | Доп. коммуникация | Очень большие модели на сотнях GPU |

**6. Итоги (инженерные выводы)**

1. Выбор стратегии параллелизма определяется топологией сети: TP — внутри узла (NVLink), PP/DP — между узлами (InfiniBand).

2. Золотое правило выбора: начать с DP, добавить TP внутри узла, затем PP между узлами, для моделей > 100B — FSDP (ZeRO-3).

3. Законы Амдала и масштабирования (Strong/Weak Scaling) позволяют прогнозировать эффективность распределённого обучения заранее.

4. FSDP радикально снижает требования к памяти одной GPU за счёт увеличения объёма коммуникации.

**Лекция 3.4. Квантизация (Quantization) и сжатие моделей**

**1. Цель лекции**
Научить студентов уменьшать размер модели и ускорять инференс ценой минимальной потери точности с помощью методов квантизации.

**2. Формируемые компетенции**

* HPC-1 (индикатор HPC-1.2) — разрабатывает эффективные вычислительные реализации параллельных алгоритмов ИИ.

**3. Основные вопросы**

3.1. Основы квантизации

* Квантизация — отображение FP32 в целочисленный диапазон (например, INT8: -128..127).

* Параметры: Scale factor (S) и Zero Point (Z); симметричная (Z=0) и асимметричная квантизация.

* Гранулярность: per-tensor, per-channel, per-group.

3.2. Классификация методов по времени применения

* Post-Training Quantization (PTQ) — применяется после обучения, требует калибровки; Weight-Only (GPTQ, AWQ) и Weight+Activation (W8A8).

* Quantization-Aware Training (QAT) — обучение с симуляцией округлений (FakeQuant), лучшая точность при агрессивном сжатии.

3.3. Специализированные техники для больших LLM

* SmoothQuant — перенос вариативности из активаций в веса для эффективного W8A8.

* LLM.int8() — смешанная декомпозиция: выбросы (outliers) в FP16, остальное в INT8, нулевая потеря качества.

* BitNet и 1.58-битная квантизация — веса до тернарных значений {-1, 0, +1}.

3.4. Инференсные движки и метрики качества

* TensorRT, OpenVINO, GGUF/llama.cpp, ONNX Runtime — основные движки для квантованного инференса.

* Perplexity (PPL) — ключевая метрика оценки качества LLM; приемлемое ΔPPL после квантизации — менее 0.5.

* Датасеты для измерения PPL: WikiText-2, C4.

**4. Ключевые определения (инженерный словарь)**

* Zero Point (Z) — значение, соответствующее нулю в квантованном представлении.

* Scale Factor (S) — коэффициент масштабирования при квантизации/деквантизации.

* GPTQ/AWQ — методы Post-Training Quantization для LLM с сохранением точности.

* Perplexity (PPL) — метрика качества языковой модели, основанная на её способности предсказывать следующий токен.

* GGUF — квантованный бинарный формат для экосистемы llama.cpp.

**5. Таблицы сравнения**

| Метод | Разрядность | Особенности |
| :---- | :---- | :---- |
| GPTQ | 4-bit | Пошаговая квантизация с компенсацией ошибки |
| AWQ | 4-bit | Активационно-взвешенная, лучшее сохранение качества |
| BitsAndBytes (NF4/FP4) | 4-bit | Интеграция с Hugging Face |
| GGUF (Q4_K_M) | ~4-bit | Формат llama.cpp, для CPU/гибридного инференса |

**6. Итоги (инженерные выводы)**

1. Квантизация — наиболее эффективный инженерный инструмент для снижения VRAM и ускорения инференса LLM.

2. При batch=1 инференс LLM ограничен пропускной способностью памяти — квантизация напрямую снижает физический предел задержки.

3. Perplexity — обязательная метрика контроля качества после квантизации; порог ΔPPL < 0.5 считается приемлемым.

4. Выбор метода квантизации зависит от целевого железа: GPU — GPTQ/AWQ/TensorRT, CPU/Edge — GGUF.
