# Методические указания преподавателям по оцениванию

Данный раздел содержит подробные инструкции для преподавателей по проведению контроля и оцениванию результатов обучения по дисциплине «Аппаратно-программные платформы для систем искусственного интеллекта».

## Критерии оценки

Используется 100-балльная шкала оценивания (как в отдельных модулях, так и в целом по дисциплине).

Критерии оценивания внутри отдельных модулей приведены ниже.

## Модуль 4

#### Практическое занятие 4.7. Бенчмаркинг и нагрузочное тестирование систем инференса LLM на базе Triton Inference Server и vLLM

Студент обязан выполнить все следующие пункты:

1. Triton-сервер успешно запущен, и модель `simple` доступна.
2. Выполнен базовый запуск `perf_analyzer -m simple`.
3. Выполнен запуск `perf_analyzer` с диапазоном параллелизма.
4. vLLM-сервер успешно запущен.
5. Создан рабочий Locust-скрипт.
6. Выполнен нагрузочный тест с генерацией отчёта.
7. Проведён хотя бы один эксперимент с оптимизацией.
8. Сдан отчёт установленной формы.

**Основания для «Незачёта»:**

- Отсутствие рабочего окружения и невозможность продемонстрировать выполнение ключевых шагов.
- Отсутствие отчёта или его формальное несоответствие требованиям.
- Плагиат (копирование чужих отчётов/скриптов без указания источника).

**Требования к отчёту**

Структура отчёта:

1. Титульный лист (ФИО, группа, дата, тема).
2. Цель работы (формулируется самостоятельно).
3. Ход выполнения (поэтапное описание с командами и скриншотами):
   - запуск Triton и `perf_analyzer`;
   - запуск vLLM и Locust;
   - эксперимент с оптимизацией.
4. Результаты (таблицы/графики с метриками).
5. Анализ результатов (интерпретация полученных данных, сравнение подходов).
6. Выводы (достигнуты ли цели, какие компетенции освоены).
7. Приложения (код Locust-скрипта, конфигурационные файлы).

**Обязательные элементы отчёта:**

- Таблица с результатами `perf_analyzer` для разных уровней параллелизма.
- График зависимости пропускной способности от параллелизма (для Triton).
- Таблица/график с результатами Locust-теста (RPS, задержки, ошибки).
- Сравнительная таблица производительности Triton и vLLM (там, где это применимо).
- Выводы о влиянии применённой оптимизации.

**Сроки сдачи:** отчёт сдаётся в электронном виде (PDF) не позднее чем через 7 календарных дней после проведения занятия.

## Назначение вариантов тестов и кейсов индустриальных партнёров

### Процедура назначения вариантов

1. **Подготовка варианта:**
   - Преподаватель генерирует уникальный вариант теста для каждого студента/группы на основе общего банка тестовых заданий.
   - Для проектного задания преподаватель подбирает кейс индустриального партнёра конкретного вуза.

2. **Кейсы индустриальных партнёров:**
   - Каждый кейс должен требовать развёртывания и настройки модели на NVIDIA Triton Inference Server на локальном GPU или виртуальной машине.
   - Кейс должен содержать реальные требования предметной области (техподдержка, документооборот, анализ данных и т. д.).
   - Минимальные требования к кейсу:
     - поставленная задача (предметная область);
     - требования к производительности (RPS, latency p50–p95–p99);
     - требования к качеству (PPL, качество ответов);
     - бюджетные ограничения (VRAM, вычислительные ресурсы);
     - временные рамки.

3. **Пример кейса:** см. [Пример кейса](../../Project/case-example.md).

4. **Распределение вариантов:**
   - Для практических работ (ПР3–ПР4, ПР5–ПР8) преподаватель может использовать общий банк задач с параметризацией.
   - Для проектной работы (КТ6) обязателен индивидуальный кейс индустриального партнёра.
   - Преподаватель фиксирует назначенный вариант в ведомости или LMS.

### Проверка кейсов индустриальных партнёров

**Перед началом проекта:**

- Преподаватель проверяет соответствие кейса требованиям (требуется ли использование Triton).
- Проверяет наличие необходимых ресурсов (GPU, Docker, доступность моделей).
- Фиксирует дедлайн сдачи проекта.

**На защите:**

- Проверяется соответствие полученного решения требованиям кейса.
- Проверяется успешное развёртывание на целевом оборудовании.
- Проверяется работоспособность через API/веб-интерфейс.

## Процедура проверки работ

### Проверка тестов

1. **Автоматическая проверка:**
   - Тесты выполняются в среде (LMS Moodle / Jupyter Notebook / Colab) с автоматической оценкой.
   - Порог прохождения: 70% правильных ответов.

2. **Ручная проверка:**
   - Открытые вопросы проверяются преподавателем вручную.
   - Кейс-задачи проверяются по эталонному решению.

3. **Пересдача теста:**
   - При неудаче (< 70%) студент имеет право на одну пересдачу в течение 3 дней.
   - При повторной неудаче — снижение оценки на 1 шаг.
   - Пересдача возможна только после повторения материалов курса.

### Проверка практических работ

1. **Техническая проверка:**
   - Выполнимость всех шагов из методического руководства.
   - Корректность команд и конфигураций.
   - Воспроизводимость результатов.

2. **Проверка отчёта:**
   - Структура отчёта (см. требования в методическом руководстве).
   - Наличие титульного листа, таблиц, графиков.
   - Обоснованность выводов.

3. **Пересдача:**
   - При неудовлетворительной оценке (< 50%) студент имеет право на пересдачу в течение 5 дней.
   - При повторной неудаче — оценка снижается на 1 шаг.
   - Пересдача проводится на индивидуальной консультации.

### Проверка проектной работы

1. **Техническая реализация (50 баллов):**
   - Развёртывание Triton/vLLM и работоспособность сервиса.
   - Обоснованность выбора модели и архитектуры.
   - Корректность настройки конфигурации.

2. **Бенчмаркинг и тестирование (25 баллов):**
   - Полнота бенчмаркинга (throughput, latency, TTFT).
   - Измеримый эффект оптимизации.
   - Соответствие требованиям кейса.

3. **Оформление и защита (25 баллов):**
   - Качество репозитория (README, структура).
   - Качество отчёта и презентации.
   - Ответы на вопросы преподавателя.

4. **Процедура защиты:**
   - Презентация (10–15 минут).
   - Демонстрация работающего сервиса.
   - Ответы на вопросы (5–10 минут).

5. **Пересдача проекта:**
   - При неудовлетворительной оценке (< 50) команда имеет право на одну пересдачу в течение 7 дней.
   - При повторной неудаче — оценка снижается на 1 шаг.
   - Пересдача требует устранения всех недочётов, отмеченных в отзыве.

## Использование LLM для автопроверки

### Область применения

LLM можно использовать для автоматизированной проверки следующих элементов:

1. **Отчёты по практическим работам:**
   - проверка структуры и наличия всех разделов;
   - проверка корректности формулировок;
   - проверка на плагиат (сравнение с источниками).

2. **Репозитории проектов:**
   - проверка наличия README и документации;
   - проверка наличия ключевых файлов (Dockerfile, config.pbtxt);
   - проверка на соответствие требованиям.

3. **Код:**
   - проверка соответствия стандартам кодирования;
   - поиск типичных ошибок.

4. **Защита:**
   - предварительная проверка презентаций;
   - генерация вопросов для защиты.

### Методика использования

**Пример промпта для проверки отчёта:**

```markdown
Ты — эксперт по методической проверке отчётов по дисциплине «Аппаратно-программные платформы для систем ИИ».

Проверь следующий отчёт по практической работе:

1. Проверь наличие всех обязательных разделов:
   - Титульный лист
   - Цель работы
   - Теоретическая часть
   - Ход выполнения
   - Результаты
   - Выводы

2. Проверь качество формулировок:
   - Правильность технической терминологии
   - Логичность изложения
   - Отсутствие ошибок

3. Проверь на плагиат:
   - Наличие оригинального текста
   - Правильное цитирование источников

4. Оцени в баллах от 0 до 10 и предоставь детальный разбор.

Отчёт:
[Вставьте текст отчёта]
```

**Пример промпта для проверки репозитория:**

```markdown
Ты — эксперт по проверке репозиториев проектных работ.

Проверь репозиторий по критериям:
1. Наличие README с описанием проекта
2. Наличие Dockerfile и docker-compose.yml
3. Наличие model_repository с config.pbtxt
4. Наличие папки benchmarks
5. Наличие папки monitoring
6. Наличие папки docs с отчётом
7. Минимум 3 коммита на участника

Проверь, что все ключевые файлы присутствуют. Оцени в процентах полноты.

Репозиторий находится по пути: [путь]
```

**Результаты автопроверки:**

- LLM не заменяет полностью ручную проверку, а используется для:
  - быстрого предварительного скрининга;
  - выявления типичных ошибок;
  - структурирования обратной связи.
- Финальная оценка формируется преподавателем с учётом результатов автопроверки и личной оценки качества работы.

### Рекомендации по использованию

1. **Для автопроверки отчётов:**
   - использовать LLM для генерации таблицы соответствия требованиям;
   - LLM проверяет структуру и терминологию;
   - преподаватель проверяет глубину анализа и корректность выводов.

2. **Для автопроверки репозиториев:**
   - LLM проверяет наличие файлов по списку;
   - преподаватель проверяет содержание файлов и качество кода.

3. **Для автопроверки презентаций:**
   - LLM проверяет структуру презентации;
   - преподаватель оценивает глубину содержания и качество выступления.
