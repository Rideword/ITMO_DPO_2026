# Методические указания для обучающихся

Настоящий документ регламентирует порядок освоения дисциплины **«Аппаратно-программные платформы для систем искусственного интеллекта»**, содержит требования к выполнению практических работ, критерии оценивания и инструкции по оформлению результатов. Документ обязателен к изучению всеми обучающимися перед началом выполнения заданий.

## 1. Общие положения

Дисциплина направлена на формирование у обучающихся системного представления об аппаратно-программных платформах для систем искусственного интеллекта и базовых инженерных практик их выбора, эксплуатации и сопровождения.

Курс охватывает гетерогенные вычислительные архитектуры (CPU, GPU, TPU, FPGA, NPU), программно-инфраструктурный слой (Linux, контейнеризация, оркестрация, CI/CD, мониторинг), проектирование вычислительной архитектуры (Roofline-модель, распределённое обучение, квантизация), а также промышленный ML-инференс на серверных кластерах и edge-устройствах.

Дисциплина ориентирована на формирование профессиональных компетенций ролей КРМ: **ML Engineer** и **MLOps** (компетенции HPC-1, LC-5).

## 2. Виды контроля и оценочные средства

Контроль освоения дисциплины осуществляется в трёх формах:

### 2.1 Текущий контроль
Проводится в течение семестра и включает:
* Тесты по теоретическим модулям — проверка усвоения теоретических основ по каждому модулю.
* Отчёты по практическим работам — документирование практических этапов профилирования, бенчмаркинга, контейнеризации и развёртывания.
* Code-review исходного кода и конфигурационных файлов (Dockerfile, скрипты профилирования, конфигурации Triton/vLLM).

### 2.2 Рубежный контроль
Проводится по завершении Модуля 1 в форме:
* Защиты проекта по выбору аппаратной платформы для сквозного кейса компании «ВидеоАналитика+» — демонстрация сравнительной матрицы и обоснование выбора платформы с использованием количественных моделей (Roofline, закон Амдала, TCO).

### 2.3 Промежуточная аттестация
Проводится по завершении семестра в форме:
* Защиты итогового проектного кейса перед комиссией — демонстрация работающего ML-сервиса с полным пайплайном от выбора модели до развёртывания и мониторинга.

## 3. Структура и содержание оценочных средств

### 3.1 Практические работы

**Общие требования к выполнению:**
1. **Ознакомление с постановкой задачи.** Внимательно изучить цель, задачи и ожидаемые результаты, указанные в методических указаниях.
2. **Планирование этапов.** Решать задачи в логической последовательности: от анализа требований к аппаратуре → к реализации → тестированию → оценке метрик.
3. **Итеративная методика.** Формулировать гипотезу оптимизации, проверять её, анализировать метрики (VRAM usage, latency, throughput), корректировать подход.
4. **Документирование.** Все этапы фиксировать в отчёте. Документирование включает исходные данные, конфигурации, скриншоты метрик (например, вывод `nvidia-smi`, `nsys`), обоснование принятых решений и выводы.
5. **Воспроизводимость.** Код должен сопровождаться файлами зависимостей (`requirements.txt`, `Dockerfile`), гарантирующими воспроизводимость окружения.
6. **Подготовка к защите.** По завершении работы проводится защита, в ходе которой необходимо пояснить логику принятых решений, продемонстрировать понимание использованных методов и ответить на контрольные вопросы.

**Перечень практических работ:**

| № | Название практической работы | Модуль |
| :--- | :--- | :--- |
| ПР1 | Профилирование GPU: nvidia-smi, DCGM, PyTorch Profiler | Модуль 1 |
| ПР2 | Бенчмаркинг платформ: ResNet-50/BERT-base — latency/throughput | Модуль 1 |
| ПР3 | Настройка ML-окружения: CUDA, nvidia-container-toolkit, верификация | Модуль 2 |
| ПР4 | Docker для ML: multi-stage образ, Docker Compose (модель+API+мониторинг) | Модуль 2 |
| ЛР5 | Roofline-анализ: определение compute-bound и memory-bound операций | Модуль 3 |
| ЛР6 | Расчёт архитектуры LLM: VRAM, пропускная способность, квантизация и перплексия | Модуль 3 |
| ЛР7 | NVIDIA Triton / vLLM: развёртывание CV или LLM, нагрузочный тест | Модуль 4 |
| ЛР8 | Финальный проектный кейс: end-to-end обучение → оптимизация → инференс → мониторинг | Модуль 4 |

### 3.2 Рубежный контроль: защита проекта по выбору платформы (Модуль 1)

**Цель:** Проверить способность анализировать вычислительную задачу, строить количественные модели и обоснованно выбирать вычислительную архитектуру.

**Формат:** Защита проекта — презентация 7–10 минут + ответы на вопросы группы.

**Требования к выполнению:**
* Презентация не должна превышать 10 слайдов.
* Чёткая визуализация сравнительной матрицы.
* Ключевые числовые данные (производительность, энергопотребление, стоимость, TCO).
* Аргументация выбора с привязкой к рассчитанным показателям (закон Амдала, арифметическая интенсивность, Roofline).

**Сквозной кейс компании «ВидеоАналитика+»** — каждому студенту выдаётся один из 10 уникальных вариантов с индивидуальными условиями (бюджет, количество потоков, объём данных, сроки, ограничения по энергопотреблению).

### 3.3 Промежуточная аттестация: защита итогового проектного кейса (Модуль 4)

**Цель:** Проверить способность спроектировать и развернуть промышленный ML-сервис на базе Triton Inference Server и/или vLLM для решения прикладной задачи, поставленной индустриальным партнёром.

**Формат:** Презентация (10–15 минут) + демонстрация работающего сервиса + ответы на вопросы комиссии.

**Критерии оценки проекта:**
1. **Техническая реализация (50 баллов):** выбор и обоснование модели, развёртывание (Triton/vLLM), проверка размещения в VRAM, экспериментальный подбор параметров оптимизации.
2. **Бенчмаркинг и тестирование (25 баллов):** проведение бенчмаркинга (`perf_analyzer`), нагрузочное тестирование (Locust), глубокий анализ и интерпретация метрик.
3. **Оформление и командная работа (25 баллов):** структурированный репозиторий, наличие коммитов от всех участников команды (минимум 3 на участника), полный и качественный технический отчёт с указанием зон ответственности.

## 4. Порядок выполнения, сдачи и защиты

### 4.1 Порядок выполнения
1. **Получение задания.** Для Модуля 1 каждому студенту выдаётся один из 10 уникальных вариантов условий сквозного кейса «ВидеоАналитика+».
2. **Анализ и расчёты.** Провести анализ задачи, рассчитать арифметическую интенсивность, оценить масштабируемость по закону Амдала, построить сравнительную матрицу с учётом TCO.
3. **Реализация.** Выполнить практическую работу, зафиксировать метрики (VRAM usage, latency, throughput, утилизация GPU) и артефакты.
4. **Документирование.** Подготовить технический отчёт в формате PDF.

### 4.2 Порядок сдачи
1. **Предварительная проверка.** Убедиться в работоспособности решения на чистом окружении (либо в предоставленном Docker-контейнере).
2. **Загрузка материалов.** Разместить в Git-репозитории или системе электронного обучения:
   * Технический отчёт в формате PDF.
   * Исходный код и конфигурационные файлы.
   * Презентацию для защиты (для ПР2 и итогового проекта).
3. **Срок сдачи.** Отчёт сдаётся не позднее 7 календарных дней после занятия (для Модулей 3–4).

### 4.3 Порядок защиты
1. **Устная презентация (10–15 минут):** постановка задачи, архитектура решения, пайплайн оптимизации и развёртывания, анализ полученных количественных метрик.
2. **Демонстрация (5–7 минут):** запуск сервиса, демонстрация обработки запросов, просмотр результатов нагрузочного тестирования или дашборда мониторинга.
3. **Ответы на вопросы (10 минут):** обоснование выбора инструментов, интерпретация результатов профилирования, предложения по масштабированию.

## 7. Политика применения систем генеративного ИИ

Использование систем генеративного искусственного интеллекта (LLM, code-assistant) в рамках дисциплины допускается при условии соблюдения следующих требований:

**Разрешённые сценарии применения:**
* Генерация шаблонного кода (boilerplate для Docker, скриптов развёртывания).
* Пояснение диагностических сообщений компилятора или логов ошибок.
* Рефакторинг и оптимизация существующего кода.
* Подготовка документации, комментариев и структурирование отчётов.

**Запрещённые сценарии применения:**
* Полная генерация отчётов или программной реализации без последующего верифицирующего анализа со стороны обучающегося.
* Использование решений, заимствованных у других обучающихся.
* Делегирование ИИ аналитических выводов, которые должны быть получены самостоятельно (например, интерпретация результатов профилирования или Roofline-анализа).

**Требование к декларированию.** Во всех сдаваемых работах обязательно наличие раздела, содержащего перечень использованных ИИ-инструментов и описание их вклада в итоговый результат. Раздел размещается в конце отчёта либо в отдельном файле `AI_USAGE.md` в корневом каталоге репозитория.

- [ ] История коммитов имеет логичную структуру, сообщения соответствуют конвенции (`feat:`, `fix:`, `docs:`).

### 8.3 Защита
- [ ] Тема и состав комиссии предварительно согласованы.
- [ ] Проведена пробная презентация и репетиция демонстрации.
- [ ] Подготовлены ответы на возможные контрольные вопросы (особенно по выбору метрик и архитектурным компромиссам).
- [ ] Демонстрационное окружение проверено и готово к показу.
- [ ] Присутствует раздел о применении ИИ-инструментов (при их использовании).
- [ ] В репозитории отсутствуют конфиденциальные данные, API-ключи и персональная информация.

## 9. Порядок консультирования

Обучающимся предоставляются следующие каналы получения консультационной поддержки:
1. **Семинарские занятия и консультации** — для обсуждения архитектурных решений и интерпретации результатов профилирования.
2. **Система Issues в репозитории** — для регистрации технических проблем среды исполнения (конфликты версий CUDA, несовместимость библиотек). Публикация проблемы в Issues способствует её оперативному разрешению для всей группы обучающихся.
3. **Рабочий канал группы** — для оперативных организационных вопросов.

> **Принципиальное требование инженерии ИИ:** полученный результат обладает ценностью исключительно при условии его воспроизводимости. Обучающимся рекомендуется уделять достаточное внимание тому, чтобы разработанное программное обеспечение и конфигурация среды могли быть развёрнуты на произвольном совместимом оборудовании.
