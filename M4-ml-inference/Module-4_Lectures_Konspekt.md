**Лекция 4.1. Серверный инференс: Triton, TorchServe, vLLM, ONNX/TRT/GGUF, batching**

**1. Цель лекции**
Сформировать у студентов представление об архитектуре промышленного серверного ML-инференса, оптимизированных форматах моделей и специализированных серверах инференса.

**2. Формируемые компетенции**

* LC-5 (индикатор LC-5.1) – осуществляет выбор инструментов и инженерных практик промышленной разработки систем ИИ, развёртывания и сопровождения моделей МО в продуктивной среде.

**3. Основные вопросы**

3.1. Введение в промышленный серверный инференс

* Отличие серверного инференса от исследовательских прототипов: высокая конкурентность (сотни-тысячи одновременных запросов), жёсткие SLA, эффективная утилизация дорогостоящих GPU-кластеров.

* Необходимость конвертации модели из исследовательского формата (PyTorch .pt/.bin) в оптимизированный формат для быстрого выполнения.

3.2. Оптимизированные форматы моделей

* ONNX (Open Neural Network Exchange) – открытый формат представления графа вычислений, обеспечивает кроссплатформенность и перенос моделей между фреймворками; ONNX Runtime выполняет инференс с аппаратным ускорением без привязки к исходному фреймворку.

* TensorRT (TRT) – SDK и компилятор NVIDIA для высокопроизводительного инференса на GPU: слияние слоёв, калибровка и квантование (FP16/INT8/FP4/FP8), динамическое управление памятью; модель сохраняется в формате engine/plan.

* GGUF (GPT-Generated Unified Format) – бинарный формат экосистемы llama.cpp для хранения квантованных моделей (вплоть до 2–3 бит на вес), ориентирован на CPU-инференс и схему CPU+GPU offloading; критичен для запуска моделей 70B+ на не топовом железе.

3.3. Серверы инференса

* NVIDIA Triton Inference Server – корпоративный стандарт для GPU-кластеров, поддерживает множество бэкендов одновременно (TensorRT, TensorFlow, PyTorch, ONNX, OpenVINO, Python); ключевые возможности: Dynamic Batching, Concurrent Model Execution, Ensemble Pipelines.

* vLLM – специализированный сервер для LLM с инновацией PagedAttention: устраняет фрагментацию VRAM через постраничное хранение KV-кэша, поддерживает continuous batching (добавление новых запросов без ожидания завершения самого длинного).

* TorchServe – официальный инструмент PyTorch для продакшен-развёртывания; модели упаковываются в формат .mar; проще в интеграции для PyTorch-only команд, но уступает Triton в мультифреймворчности, а vLLM – в скорости генерации LLM.

3.4. Dynamic Batching и протоколы

* Dynamic Batching – автоматическое объединение входящих запросов в батчи на лету для повышения пропускной способности без существенного увеличения задержки одного запроса.

* Model Repository – структура хранения версий моделей и конфигураций для сервера инференса.

* Протоколы HTTP/gRPC для взаимодействия клиента с сервером инференса.

**4. Ключевые определения (инженерный словарь)**

* ONNX Runtime – кроссплатформенная среда исполнения моделей в формате ONNX.

* TensorRT engine/plan – скомпилированный и оптимизированный под конкретное GPU артефакт модели.

* GGUF – квантованный бинарный формат для CPU/гибридного инференса LLM.

* Dynamic Batching – объединение запросов в батч в реальном времени сервером инференса.

* Continuous Batching – схема батчинга vLLM, позволяющая добавлять/удалять запросы на каждом шаге генерации.

* Model Repository – структурированное хранилище версий моделей для Triton.

**Лекция 4.2. Оптимизация инференса: PagedAttention, Flash Attention, Speculative Decoding, KV-cache**

**1. Цель лекции**
Сформировать у студентов понимание алгоритмических оптимизаций инференса LLM и умение измерять и интерпретировать ключевые метрики производительности сервиса.

**2. Формируемые компетенции**

* HPC-1 (индикатор HPC-1.2) – разрабатывает эффективные вычислительные реализации параллельных алгоритмов ИИ.

**3. Основные вопросы**

3.1. Проблема памяти в инференсе LLM

* Инференс LLM кардинально отличается от инференса классических моделей: на первый план выходит не вычислительная сложность (FLOPs), а пропускная способность памяти.

* Механизм self-attention имеет квадратичную сложность O(n²) по памяти и времени относительно длины последовательности.

3.2. Flash Attention

* Классическая реализация внимания материализует полную матрицу внимания O(n²) в HBM, что делает операцию memory-bound.

* Tiling – разбиение матриц Q, K, V на блоки, загружаемые в быструю SRAM (shared memory).

* Online Softmax – итеративный пересчёт softmax по мере обработки блоков без хранения полной матрицы.

* Kernel Fusion – слияние матричных умножений, softmax и нормализации в единый CUDA-kernel для минимизации обращений к HBM.

* Результат: ускорение инференса в 2–4 раза, снижение потребления памяти, возможность обработки более длинных контекстов.

3.3. PagedAttention

* Ключевая инновация vLLM, заимствующая идею виртуальной памяти ОС для управления KV-кэшем.

* Блоки и страницы – KV-кэш разбивается на блоки фиксированного размера (например, 16 токенов), хранящиеся в VRAM не непрерывно.

* Block Table – таблица отображения логических блоков токенов на физические блоки памяти.

* Copy-on-Write – разделение общих префиксов токенов между запросами при beam search/parallel sampling.

* Результат: потери памяти снижаются до ~4% (против 60–80% во традиционных системах), batch size увеличивается в 2–4 раза.

3.4. Speculative Decoding

* Метод ускорения decode-фазы: небольшая «черновая» модель предсказывает несколько токенов вперёд, основная модель проверяет их за один проход.

* Позволяет сократить количество последовательных шагов декодирования при сохранении точности основной модели.

3.5. Метрики инференса LLM: TTFT, TPOT, P99

* Prefill-фаза – обработка входного промпта, все токены параллельно, compute-bound.

* Decode-фаза – последовательная генерация токенов, memory-bound.

* TTFT (Time To First Token) – время до генерации первого токена; критично для интерактивных чат-ботов.

* TPOT (Time Per Output Token) – среднее время генерации одного выходного токена; определяет скорость «печати» ответа.

* E2E Latency – TTFT + (N_tokens × TPOT).

* P99 – критически важный перцентиль: средние значения (mean, p50) вводят в заблуждение, «хвосты» распределения определяют реальный опыт пользователей и соответствие SLA.

* Trade-off: увеличение batch size улучшает TPOT и throughput, но ухудшает TTFT; решение – Chunked Prefill (разбиение промпта на чанки, чередование с decode-шагами).

**4. Ключевые определения (инженерный словарь)**

* Flash Attention – IO-осознанный точный алгоритм вычисления внимания без материализации полной матрицы O(n²).

* PagedAttention – управление KV-кэшем по аналогии с виртуальной памятью ОС.

* Speculative Decoding – ускорение генерации через предсказание токенов «черновой» моделью с последующей верификацией.

* TTFT/TPOT – ключевые метрики латентности LLM-инференса.

* Chunked Prefill – разбиение длинного промпта на чанки, чередуемые с decode-шагами других запросов.

**5. Таблицы сравнения**

| Оптимизация | Решаемая проблема | Эффект |
| :---- | :---- | :---- |
| Flash Attention | Memory-bound вычисление attention | Ускорение 2–4×, снижение памяти |
| PagedAttention | Фрагментация VRAM для KV-cache | Потери памяти ~4% вместо 60–80% |
| Speculative Decoding | Последовательность decode-фазы | Сокращение числа шагов генерации |

**6. Итоги (инженерные выводы)**

1. Оптимизация LLM-инференса — область на стыке алгоритмических инноваций и архитектуры высокопроизводительных вычислений.

2. Понимание фаз prefill/decode необходимо для выбора правильной оптимизации под конкретное узкое место.

3. P99, а не среднее значение, должен быть основным критерием при нагрузочном тестировании production-сервиса.

4. Trade-off между TTFT и TPOT решается инженерными методами (Chunked Prefill), а не выбором «одной верной» настройки батча.

**Лекция 4.3. Edge AI: Jetson Orin, Hailo-8, TFLite, CoreML, RKNN, OTA**

**2. Формируемые компетенции**

**3. Основные вопросы**

3.1. Ключевые ограничения и требования Edge

* Жёсткие лимиты энергопотребления (TDP): от 5 Вт до 30 Вт.

* Offline-режим: автономная работа при потере связи с облаком.

* Минимальная латентность: реакция на события за миллисекунды без задержек на передачу данных.

* Гетерогенная архитектура: использование CPU/GPU и специализированных нейропроцессоров (NPU, DLA, TPU).

3.2. Аппаратная экосистема Edge-устройств

* NVIDIA Jetson – SoC с GPU архитектуры Ampere/Ada Lovelace, ARM CPU, DLA-ускорители; полная поддержка серверного стека NVIDIA (CUDA, TensorRT, Triton), бесшовный перенос моделей из дата-центра.

* Hailo AI (Hailo-8/Hailo-10) – специализированные процессоры для инференса нейросетей, экстремальная энергоэффективность (до 26 TOPS при ~2.5 Вт); требует компиляции в формат HEF.

* Google Coral (Edge TPU) – ориентирован на модели, жёстко квантованные до INT8; простая интеграция, но специфический пайплайн конвертации.

* Rockchip (RK3588 и аналоги) – встроенный NPU (до 6 TOPS), популярен для промышленных шлюзов и камер, требует проприетарных тулчейнов.

3.3. Форматы моделей для Edge

* TensorFlow Lite (TFLite) – облегчённый фреймворк для мобильных/Edge устройств, формат .tflite; поддерживает Post-Training Quantization (PTQ) и Quantization-Aware Training (QAT); делегирование выполнения на аппаратные ускорители (GPU Delegate, NNAPI, Coral Edge TPU Delegate).

* RKNN (Rockchip Neural Network) – проприетарный формат/тулчейн для NPU Rockchip; модели конвертируются из ONNX/PyTorch/TFLite через RKNN Toolkit в формат .rknn; требует калибровочного датасета для точного INT8-квантования, ошибки конвертации критически влияют на accuracy.

* CoreML – формат Apple для инференса на устройствах экосистемы iOS/macOS с использованием Neural Engine.

3.4. OTA-обновления и автономность

* OTA (Over-The-Air) – удалённое обновление модели/прошивки на распределённом парке устройств без физического доступа.

* Требования к OTA для Edge AI: атомарность обновления, возможность откат (rollback), верификация целостности модели перед развёртыванием.

**4. Ключевые определения (инженерный словарь)**

* TDP (Thermal Design Power) – проектная тепловая мощность устройства.

* DLA (Deep Learning Accelerator) – специализированный блок инференса в составе SoC Jetson.

* HEF (Hailo Executable Format) – формат компиляции моделей для процессоров Hailo.

**Лекция 4.4. MLOps для инференса: model registry, A/B-тест, canary, drift detection**

**1. Цель лекции**
Сформировать у студентов представление об инженерных практиках сопровождения продуктивных моделей: версионирование, безопасное обновление и непрерывный мониторинг ML-сервисов.

**2. Формируемые компетенции**

* LC-5 (индикатор LC-5.1) – осуществляет выбор инструментов и инженерных практик промышленной разработки, развёртывания и сопровождения моделей МО в продуктивной среде.

**3. Основные вопросы**

3.1. Проблема деградации моделей

* Развёртывание модели — не финальная точка, а начало этапа эксплуатации.

* Модели МО подвержены «деградации»: изменение входных данных или бизнес-контекста снижает точность со временем.

3.2. Управление артефактами: Model Registry

* Недопустимо использование локальных файлов вида model_final_v2_really_final.pt в промышленной разработке.

* Model Registry – централизованное хранилище, связывающее артефакт модели с метаданными: версия, автор, метрики обучения, стадия жизненного цикла, зависимости.

* Жизненные стадии: None (разработка) → Staging (пре-продакшен) → Production (активный инференс) → Archived (снята с поддержки).

* MLflow Model Registry – индустриальный стандарт, интегрируется с CI/CD для автоматического продвижения модели в Production при успешном прохождении тестов.

3.3. Стратегии безопасного развёртывания

* Прямая замена (big bang deployment) запрещена в высоконагруженных системах.

* Canary Deployment – новая версия модели развёртывается параллельно со старой на небольшую долю трафика (например, 5%), минимизируя «радиус поражения»; доля трафика постепенно увеличивается (20% → 50% → 100%). Инструмент: Seldon Core/KServe для декларативной настройки traffic splitting в Kubernetes.

* A/B-тестирование – трафик разделяется между моделями на значительном промежутке времени; цель – сравнение бизнес-метрик (конверсия, CTR, удержание), а не только технических.

3.4. Мониторинг и обнаружение дрейфа (Drift Detection)

* Системный мониторинг: доступность сервиса, latency, использование GPU/CPU, ошибки (5xx).

* ML-мониторинг: оценка качества предсказаний модели в реальном времени.

* Data Drift (ковариативный сдвиг) – изменение распределения входных признаков P(X). Пример: модель обучалась на дневных фото, а в продакшен поступают ночные снимки.

* Concept Drift (сдвиг концепции) – изменение взаимосвязи между признаками и целевой переменной P(Y|X). Пример: изменение макроэкономических условий меняет паттерны спроса.

* Evidently AI – библиотека для расчёта метрик дрейфа, сравнивает референсный набор с текущими данными инференса, генерирует дашборды по статистическим тестам (Колмогоров-Смирнов, PSI); при превышении порогов инициируется алерт/переобучение.

**4. Ключевые определения (инженерный словарь)**

* Model Registry – централизованное хранилище версий моделей с метаданными.

* Canary Deployment – постепенное развёртывание новой версии на ограниченную долю трафика.

* A/B-тестирование – сравнение бизнес-метрик двух версий модели на параллельном трафике.

* Data Drift / Concept Drift – два типа дрейфа, влияющие на качество модели в продакшене.

* PSI (Population Stability Index) – статистическая метрика для оценки сдвига распределения данных.

**5. Таблицы сравнения**

| Практика | Цель | Инструмент |
| :---- | :---- | :---- |
| Model Registry | Версионирование и трассируемость артефактов | MLflow |

| A/B-тестирование | Доказательство превосходства новой модели | Seldon Core, кастомные пайплайны |

**6. Итоги (инженерные выводы)**

1. Промышленный инференс — это не просто запуск model.predict(), а выстроенный конвейер сопровождения модели.

2. Model Registry обеспечивает трассируемость и управляемость жизненного цикла модели.

3. Canary и A/B-тестирование решают разные задачи: безопасность внедрения против доказательства бизнес-превосходства.

4. Только совокупность практик (Model Registry + Canary/A-B + Drift Detection) гарантирует стабильную бизнес-ценность ML-сервиса на всём жизненном цикле.
